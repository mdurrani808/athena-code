# `nav_sim_harness` — Implementation Plan

End-to-end Gazebo harness for the Athena nav stack. Mirrors the manual workflow:

```
ros2 launch simulation     bringup.launch.py publish_sim_heading:=true
ros2 launch nav_bringup    emmn.launch.py    sim:=true
ros2 run    mission_executive mission_cli   nav post1 38.40 -110.79
```

…and adds spawning of mission artifacts, scripted scenarios, and pass/fail scoring.

## What this proves / doesn't

**Proves:** mission_executive state machine, planner/executive integration, TF wiring, GPS→ENU path, abort/advance/skip/teleop flow, LED transitions, replan-on-stuck, spiral coverage, ArUco-approach branch, regressions.

**Does not prove:** perception accuracy, control tuning, sensor-noise behavior. Field testing still required for anything sensor-coupled.

## Verified interfaces

**Goal injection — use `mission_cli` directly (subprocess).** It is already a working, blocking action client with all the goal types we need:
```
ros2 run mission_executive mission_cli nav    gps    <lat> <lon> [tol]
ros2 run mission_executive mission_cli nav    meter  <x>   <y>   [tol]
ros2 run mission_executive mission_cli nav    post1  <lat> <lon> [tol]   # ARUCO_POST_1
ros2 run mission_executive mission_cli nav    post2  <lat> <lon> [tol]   # ARUCO_POST_2
ros2 run mission_executive mission_cli set-target gps   <id> <lat> <lon> [type] [tol]
ros2 run mission_executive mission_cli set-target meter <id> <x>   <y>   [type] [tol]
ros2 run mission_executive mission_cli nav-by-id  <id> [is_return]
ros2 run mission_executive mission_cli abort | teleop on|off | status
```
Each `nav …` invocation blocks until the action result, prints success/message, then exits. **Exit code is NOT a pass/fail signal** — `mission_cli` returns 0 on both successful and failed navs (it only `sys.exit(1)`s on usage errors). The runner therefore scores off the background `/nav_status` observer (see Phase 2), never the subprocess exit code. (Alternative if we want the CLI to be authoritative: patch `mission_cli` to exit non-zero on a non-success action result — ~3 lines. Not doing this in v1.)

**Observation topics (verified):**
- `/led_status` (`msgs/LedStatus`) — `CMD_FLASH` + green = arrived. Note: also fires on `STOPPED_AT_RETURN` and `SPIRAL_DONE`, so always AND it with the expected `state`; never score on LED alone.
- `/nav_status` (`msgs/NavStatus`) — `state` (string), `distance_to_goal_m`, `cross_track_error_m`.
- `/active_target` (`msgs/ActiveTarget`).
- `/aruco_loc` (`vision_msgs/Detection2D`) — published by `aruco_detection/aruco_node.py`. **Confirm `emmn.launch.py`'s aruco launch brings up this node, not `aruco_detection/dummy_BB_node.py`** — the dummy also publishes `/aruco_loc` but as a different `BB` message type. (Not used by v1 scoring, which relies on LED + state + ground-truth proximity.)
- `/odom/ground_truth` (bridged from Gz) — used for proximity scoring.

(YOLO / object-detection scoring is out of scope for v1 — added later; see *Future work*.)

## Verified Gz integration

- World name default = `default`, world file default = `empty.sdf`. Both exposed by `bringup.launch.py`.
- `GZ_SIM_RESOURCE_PATH` already includes `description/`'s parent and `description/models/` (set in `gz_sim.launch.py`, lines 18–24 — **not** `spawn.launch.py`). A new model dropped in `src/description/models/aruco_post/` resolves via `model://aruco_post` with no env change.
- `bridge.launch.py` bridges clock, mag, ZED RGB+cloud, ground-truth odom. **No spawn service bridged today** — harness must add it.
- **`marker0` is not the URC post.** Build a new `aruco_post` model — triangular prism, 0.5–1.5 m off ground, three identical 4x4_50 tag textures (one per face), 20×20 cm faces with a 1-cell white border (2.5 cm/cell). Textures generated by `cv2.aruco.generateImageMarker` so any tag id works.

## Changes to existing launch files (no parallel files)

Add a `headless` arg, default `false`, to both:

- **`src/simulation/launch/gz_sim.launch.py`** — accept `headless`; when `true`, append `-s` to `gz_args` (server-only, sensors still render, no GUI).
- **`src/simulation/launch/bringup.launch.py`** — declare `headless`, forward to the `gz_sim` include.

That's the entire change to existing code. `harness.launch.py` then just passes `headless:=true` through.

## Layout

```
nav_sim_harness/
├── CMakeLists.txt, package.xml
├── launch/harness.launch.py        # includes both stacks + adds spawn-service bridge
├── nav_sim_harness/
│   ├── __init__.py
│   ├── spawner.py                  # Gz create-service client + inline SDF templates
│   └── runner.py                   # YAML loader, mission_cli subprocess driver, scoring
├── scripts/
│   ├── run.sh                      # ./run.sh scenarios/foo.yaml [--headless]
│   └── gen_aruco_texture.py        # ONE-SHOT dev tool: cv2.aruco.generateImageMarker → PNG.
│                                   #   Run by hand to bake a tag into the model below; NOT
│                                   #   imported by the harness and NOT run at spawn time.
├── scenarios/
│   ├── smoke.yaml
│   ├── single_aruco_post.yaml
│   └── urc_full_mission.yaml

src/description/models/aruco_post/  # new shared model (lives in description, not harness)
├── model.sdf                       # 3-sided prism + post; references the baked texture
└── materials/textures/             # pre-generated tag PNG(s), committed; baked at model-build time
```

`aruco_post` lives in `description/` so other simulation work can reuse it. Tag textures are
**pre-generated once** with `gen_aruco_texture.py` and committed into the model's `materials/` — the
running harness just spawns the finished model at a pose, with no runtime texture generation. To
support a different tag id, re-run the tool and commit the new PNG (default committed id = 4).

## Phases

### Phase 1 — Launch-file flag + spawner (1 day)
- Add `headless` arg to `simulation/launch/gz_sim.launch.py` and `bringup.launch.py`.
- Add `/world/default/create` bridge (using `ros_gz_bridge parameter_bridge` for `ros_gz_interfaces/srv/SpawnEntity`) inside `harness.launch.py`.
- `spawner.py`: rclpy client → `spawn_box(pose, size)`, `spawn_aruco_post(pose)`. Jinja SDF strings inline. `spawn_aruco_post` just instantiates the pre-built `model://aruco_post` at a pose — no runtime texture work. (Mallet/object spawner added with YOLO scoring later.)
- **One-shot, before building the spawner:** run `gen_aruco_texture.py` to produce the id=4 tag PNG, then build the `description/models/aruco_post` model (prism geometry + the baked texture in `materials/`) and commit both. This tool is not part of the harness runtime.
- **Done when:** REPL/script can drop a box and the pre-built ArUco post (id=4) into a running `terrain_world.sdf`, headless.

### Phase 2 — Scenario runner via mission_cli (1 day)
- `runner.py`:
  1. Load YAML scenario.
  2. Wait for `/mission_executive/navigate_to_target` action server and `/nav_status` to publish.
  3. Execute steps in order: each step is either `spawn:` (call spawner) or `cli:` (run `mission_cli` subprocess and capture exit code + stdout).
  4. Background-subscribe to `/nav_status`, `/led_status`, `/odom/ground_truth` for scoring.
  5. After each `cli:` step that runs a nav, evaluate the step's `assert:` block.
- Scoring rules (URC §1.f, v1 scope):
  - GNSS: `nav_status.state == STOPPED_AT_TARGET` and `distance_to_goal_m < 3.0`.
  - ArUco post: `STOPPED_AT_TARGET` + `led_status` flashing green + ground-truth distance to spawned post < 2.0 m.
  - Object: deferred (see *Future work*).
- YAML schema (one step = one CLI call, optionally preceded by spawns):
  ```yaml
  name: single_aruco_post
  world: terrain_world.sdf
  world_name: default
  timeout_s: 240
  setup:
    - spawn: {type: aruco_post, tag_id: 4, pose: [12, 3, 0, 0, 0, 0]}
  steps:
    - cli: nav post1 38.40650 -110.79180 13
      assert: {kind: aruco_post, max_dist_m: 2.0, expect_state: STOPPED_AT_TARGET}
  ```
- **Done when:** `./run.sh scenarios/single_aruco_post.yaml` exits 0 with a pass/fail summary printed.

### Phase 3 — Launch wrapper + URC scenario (0.5 day)
- `harness.launch.py`:
  - includes `simulation/bringup.launch.py` with `publish_sim_heading:=true`, `world:=…`, `headless:=…` forwarded. (`publish_ground_truth_tf` not needed — see Open items #1.)
  - includes `nav_bringup/emmn.launch.py` with `sim:=true`.
  - adds the `/world/<name>/create` bridge.
- `scripts/run.sh`: `ros2 launch nav_sim_harness harness.launch.py` in the background, then `python -m nav_sim_harness.runner <scenario>`, then teardown.
- Author `smoke.yaml`, `single_aruco_post.yaml`, and a `multi_target.yaml` that chains GNSS + post targets via `set-target` + `nav-by-id` to mirror the operator flow. `smoke.yaml` is the smoke test — a minimal scenario (action server + `/nav_status` come up, one short nav) run through the same `run.sh`/runner path as every other scenario. No separate `launch_testing`/`colcon test` harness.
- **Done when:** one command runs the full mission headlessly and `./run.sh scenarios/smoke.yaml` exits 0.

**Total: ~2.5 dev-days.**

## Conventions

- Scenarios assert ranges, never exact poses — Gz physics is not bit-reproducible.
- Goals always go through `mission_cli`. The harness never directly calls the action server — that keeps the test path identical to the operator path.
- All YAML poses are in the sim world frame (ENU, origin = sim spawn). GPS args in YAML are passed verbatim to `mission_cli`; conversion is done by `gps_pose_publisher` at runtime.
